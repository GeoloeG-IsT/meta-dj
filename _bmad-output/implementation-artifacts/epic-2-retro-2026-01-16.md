## What Didn't Go Well

### 100% Review Fix Rate

Every story required fixes during code review. While this shows reviews are effective, it indicates issues aren't being prevented upfront.

### Stem Model Not Deployed (Feature Blocker)

Story 2.5 code is complete but the ONNX model (`/models/demucs-lite.onnx`) is not deployed. The feature cannot be used until the ~80MB model is hosted and downloadable.

**Impact:** Users cannot use stem separation despite complete code implementation.

### Features Marked Complete But Unwired

Two stories had features that were implemented in isolation but never connected:
- **Story 2.3:** TransientDetector was fully implemented with 22 tests but never wired to the UI
- **Story 2.5:** "Clear Stems" task marked complete but no context menu existed

**Pattern:** Unit tests on isolated functions don't catch integration gaps.

### Analysis on Main Thread (Tech Debt)

Story 2.2's track analysis runs on main thread, documented as a deviation from Split-Brain architecture. This creates potential performance issues during analysis of long tracks.

## Key Insights

1. **Code reviews are our safety net, but we're over-relying on them** - 100% fix rate means prevention is lacking
2. **Unit tests don't catch integration gaps** - Features can be fully tested in isolation but never wired up
3. **External dependencies need deployment plans** - Code without the model is incomplete
4. **'Task complete' ≠ 'Feature works end-to-end'** - Must verify full user path
5. **Story-to-story knowledge transfer works well** - Dev Notes prevented repeated mistakes
